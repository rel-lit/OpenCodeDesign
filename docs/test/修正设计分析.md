# 设计子代理（GraphAgent）架构偏离分析与修正方案

## 1. 当前问题总结

### 1.1 根本原因：把“全量图状态注入提示词”当作记忆机制

当前实现中，`buildGraphAgentPrompt` 把整个 `graphState`（contexts、nodes、edges、prototypes、working sets、version）全部序列化为 JSON，作为子代理的输入。后续为了不在用户聊天时间线显示这个巨大的 JSON，又进一步把它拆到 `system` 提示词里。

这是错误的设计：
- **图状态不是提示词，而是被管理的工作记忆**。OpenCode 已经提供了 `activeWorkingSet` 和 `temporaryWorkingSet` 两套机制来聚焦子代理的注意力范围。
- **把完整数据库快照塞进 prompt 是不可持续的**。图变大后 token 会爆炸，而且子代理被淹没在无关信息中。
- **用 `system` 字段绕过问题** 是在粘合代码，而不是在正确架构层解决问题。

### 1.2 已经造成的架构偏离

#### A. 通用 `task` 工具被特化

在 `packages/opencode/src/tool/task.ts` 中新增：

```ts
system: Schema.optional(Schema.String).annotate({
  description: "Additional system context for the agent, shown only in the context tab, not the chat timeline",
})
```

并在 `runTask` 中把它传给 `ops.prompt({ system: params.system, ... })`。

**问题**：`task` 是通用子代理工具，不应该为 GraphAgent 的提示词渲染问题单独增加字段。如果 system prompt 需要扩展，应该通过 agent 配置、instruction 或 session context 机制，而不是 task 参数。

#### B. `buildGraphAgentPrompt` 返回 `{ prompt, system }`

原来返回一个字符串（JSON），现在返回一个对象，把用户请求和图状态 JSON 分开。

**问题**：这个函数的职责应该是“构造给 GraphAgent 的输入”。它不应该知道子代理对话框里显示什么、system prompt 里放什么。这些属于 session/LLM 编排层。

#### C. 图状态以 JSON 形式出现在子代理输入中

无论是 user message 还是 system message，本质上都是在把内部数据库状态直接喂给 LLM。

**问题**：GraphAgent 的 prompt 应该告诉它“如何获取信息”（通过读取工具和工作集工具），而不是直接给它所有信息。

### 1.3 原来的哪些改动是相对合理的

- `SessionDesignApprovalDock` 和对应 CSS：把设计审批问题渲染成专用面板，方向正确。
- `design_finalize_change` 替代 `design_apply_changes`/`design_clear_changes`：实现 two-stage approval 的终稿提交，方向正确。
- `message-part.tsx` 中把 design subagent 的 subtitle 固定为 agent description：避免把用户 prompt 截断显示在 task 卡片上，方向正确。
- `formatPendingDelta` 用语义名称替换 raw ID：终稿展示需要人类可读，方向正确。

## 2. 正确的设计应该是什么

### 2.1 GraphAgent 的记忆与上下文机制

OpenCode 已经为 GraphAgent 设计了记忆管理：

- **Active Working Set（活跃工作集）**：用户/ChatAgent 明确关注的设计范围。子代理应该优先在这个范围内工作。
- **Temporary Working Set（临时工作集）**：子代理自己为了分析而扩展的范围。子代理通过 `design_workset_add` / `design_workset_expand` 等工具主动管理。
- **读取工具**：`design_get_context`、`design_get_concept`、`design_find_concepts`、`design_get_relations` 等，按需查询。

GraphAgent 的输入应该：
1. 包含当前请求（用户问题或变更意图）。
2. 包含 active working set 的摘要（名称、ID、容量），让子代理知道用户当前关注什么。
3. **不包含**完整图状态。子代理需要自己用工具读取。
4. 如果必须给上下文，只给高度压缩的摘要，例如：
   - 有多少个 context、node、edge、prototype
   - active working set 里有哪些上下文和概念名称
   - 版本号

### 2.2 子代理对话框应该显示什么

子代理会话的第一条用户消息，是调用 `task` 工具时传入的 `prompt`。这个 prompt 应该是：

> “请详细介绍当前设计图中所有的概念、关系、限界上下文以及它们之间的关联”

而不应该是：

> `{ "mode": "cognition", "graphState": { ...巨型 JSON... } }`

如果子代理需要内部上下文，应该通过 session context tab 或系统提示词透明地附加，但**不应该是用户消息内容本身**。

### 2.3 提示词注入的位置

如果确实需要给 GraphAgent 一些“系统级”上下文（比如版本号、工作集摘要），正确位置是：

1. **Agent 配置**：`design-graph` agent 的 `prompt` 或 `instruction` 文件。这是 OpenCode 的 agent 系统提示词机制。
2. **Session instruction**：`SessionPrompt` 的 instruction 系统，可以在子代理 session 启动时注入额外上下文。
3. **不要通过 `task` 参数注入**。

## 6. 与 OpenCode 上游源码对比结果

### 6.1 上游关键发现

从 `https://github.com/anomalyco/opencode` 拉取干净 `dev` 分支后，发现：

- **上游没有 design/GraphAgent 子系统**。`packages/opencode/src/design/`、`packages/opencode/src/tool/design.ts` 等文件在上游不存在。
- **design 子系统是当前项目 `OpenCodeDesign` 自己的魔改内容**，不是从上游 fork 来的。
- 因此，上游的作用是作为**架构参照物**，用来判断当前项目的 design 改动是否遵循了 OpenCode 的通用模式。

### 6.2 上游 `task` 工具的原本设计

`packages/opencode/src/tool/task.ts` 上游版本：

```ts
const BaseParameterFields = {
  description: Schema.String.annotate({ description: "A short (3-5 words) description of the task" }),
  prompt: Schema.String.annotate({ description: "The task for the agent to perform" }),
  subagent_type: Schema.String.annotate({ description: "The type of specialized agent to use for this task" }),
  task_id: Schema.optional(Schema.String).annotate({ ... }),
  command: Schema.optional(Schema.String).annotate({ description: "The command that triggered this task" }),
}
```

没有 `system` 参数。

`runTask` 中调用 `ops.prompt` 时也没有 `system` 字段：

```ts
const result = yield* ops.prompt({
  messageID: MessageID.ascending(),
  sessionID: nextSession.id,
  model: { modelID: model.modelID, providerID: model.providerID },
  variant: next.model ? undefined : variant,
  agent: next.name,
  parts,
})
```

**结论**：`task` 工具的职责是启动子代理，并把 `prompt` 作为用户消息传给子代理。它**不应该**负责注入 system prompt 或隐藏内部上下文。这是通用通道，不能被 GraphAgent 特化。

### 6.3 上游 `PromptInput.system` 的用途

`packages/opencode/src/session/prompt.ts` 中 `PromptInput` 有 `system: Schema.optional(Schema.String)`，并且会把它存到 `SessionV1.User.system` 中。

在 `LLMRequestPrep.prepare` 中：

```ts
const system = [
  [
    ...(input.agent.prompt ? [input.agent.prompt] : SystemPrompt.provider(input.model)),
    ...input.system,
    ...(input.user.system ? [input.user.system] : []),
  ]
    .filter((x) => x)
    .join("\n"),
]
```

说明：
- `input.system` 来自 `LLM.stream` 调用时的 `system` 参数（session-level）。
- `input.user.system` 来自用户消息的 `system` 字段（per-message）。
- 二者都会被拼接到最终的 system prompt 中。

但关键点是：**上游没有任何地方从 `task` 工具注入 `system` 字段**。`PromptInput.system` 是为 session 编排层预留的，不是为工具参数预留的。

### 6.4 上游 agent 配置怎么承载系统提示词

`packages/opencode/src/agent/agent.ts` 中 `Agent.Info` 有：

```ts
prompt: Schema.optional(Schema.String),
```

每个 agent 都可以有自己的 `prompt`（例如 `PROMPT_EXPLORE`、`PROMPT_COMPACTION`）。这个 `prompt` 会被拼接到 system prompt 最前面（见 `LLMRequestPrep.prepare`）。

**结论**：如果 GraphAgent 需要系统级上下文说明，正确位置是 agent 的 `prompt` 字段（即 `graph.txt`），或者是运行时通过 instruction 机制注入，而不是通过 task 参数。

### 6.5 上游 instruction 系统

`packages/opencode/src/session/instruction.ts`：

- 从 `AGENTS.md`、`CLAUDE.md`、`CONTEXT.md`、config 中的 `instructions` 等读取系统指令。
- `instruction.system()` 返回字符串数组，被 `SessionPrompt` 在每次请求时拼接到 system prompt。

**结论**：这是 OpenCode 标准的“额外系统上下文”注入机制。如果 GraphAgent 需要动态上下文，应该通过 instruction 系统扩展，而不是 task 参数。

### 6.6 上游子代理对话框显示什么

上游没有任何特殊逻辑隐藏子代理的第一条用户消息。`task` 工具的 `prompt` 会被 `resolvePromptParts` 解析成 `parts`，然后作为子代理 session 的第一条用户消息。

这意味着：
- 子代理对话框里看到的就是 `prompt` 内容。
- 如果 `prompt` 是巨型 JSON，用户就会看到巨型 JSON。
- **正确做法是让 `prompt` 本身保持人类可读**，而不是想办法把它藏起来。

### 6.7 当前项目相对上游已有的设计子系统改动

当前项目相对上游已经做了大量 design 子系统改动：

- `packages/opencode/src/design/` 整个目录（上下文、节点、边、原型、变更累积器、版本同步等）。
- `packages/opencode/src/tool/design.ts` 所有 design 工具。
- `packages/opencode/src/agent/agent.ts` 中新增 `design-graph`、`design-search`、`design-chat` 三个 agent。
- `packages/app/src/pages/session/composer/session-design-approval-dock.tsx` 审批面板。

这些都是当前项目自己的实现，不是上游内容。

## 7. 修正方案（更新）

基于上游架构参照，修正方案必须遵守以下原则：

1. **通用 `task` 工具不允许特化**。移除 `system` 参数和相关注入逻辑。
2. **GraphAgent 的输入必须保持人类可读**。`prompt` 应该是简短请求文本。
3. **图状态不注入 prompt**。GraphAgent 通过读取工具和工作集工具自己获取。
4. **如果需要系统级上下文说明，放在 agent `prompt` 或 instruction 中**，而不是 task 参数或用户消息。
5. **审批面板和 two-stage approval 保留**，这是当前项目的合理功能。

### 7.2 新的 `buildGraphAgentPrompt` 输入设计

GraphAgent 的输入应该是一个**轻量、人类可读**的 prompt，例如：

```text
mode: cognition
request: 请详细介绍当前设计图中所有的概念、关系、限界上下文以及它们之间的关联。

当前活跃工作集（active working set）：
- 上下文：太空探索、战斗系统
- 概念：玩家、飞船、星球、资源、任务、敌人、武器、生命值、伤害
- 容量：20 / 20

当前设计图版本：7

请使用可用的读取工具和工作集工具获取完整图状态，然后回答用户问题。
```

**不包含**：完整 contexts/nodes/edges/prototypes JSON。

### 7.3 GraphAgent 的 system prompt（`graph.txt`）修正

`graph.txt` 应该：
1. 说明 GraphAgent 的身份和职责。
2. 说明可用工具。
3. 说明工作集机制。
4. **明确说**：图状态不会自动注入 prompt，必须通过工具读取。
5. 保留 two-stage approval 的流程说明。
