# GraphAgent 架构偏离与工作集机制最终修正方案（提交审批 - 整合版）

## 1. 问题根源

### 1.1 我的根本错误

我把 **“全量图状态注入 prompt”** 当作了 GraphAgent 的记忆/上下文解决方案，反复在错误方向上修补：

1. **第一轮**：`buildGraphAgentPrompt` 把完整 `graphState` JSON 注入 user message。
2. **第二轮**：用户反馈看到一堆 ID，我把 ID 装饰成 `名称 (id)`，继续往 prompt 里塞数据库状态。
3. **第三轮**：为了隐藏 JSON，我给通用 `task` 工具加了 `system` 参数，把图状态 JSON 塞进 system prompt，用胶水代码掩盖架构问题。

**核心错误**：我没有把 **活跃工作集 / 临时工作集** 当作真正的记忆机制来使用，而是绕过了它。

### 1.2 造成的架构偏离

| 改动 | 位置 | 性质 |
|---|---|---|
| 给通用 `task` 工具加 `system` 参数 | `packages/opencode/src/tool/task.ts` | **严重破坏通用子代理通道抽象** |
| `buildGraphAgentPrompt` 返回 `{ prompt, system }` | `packages/opencode/src/tool/design.ts` | 把 prompt 构造层和 LLM 渲染层混为一谈 |
| 完整 `graphState` JSON 注入 prompt | `packages/opencode/src/tool/design.ts` | 架空工作集机制，把数据库状态当 prompt |
| ID 语义化装饰 | `packages/opencode/src/tool/design.ts` | 在错误方向上继续修补 |
| `graph.txt` 说明 JSON 在 system prompt 里 | `packages/opencode/src/design/agent/prompt/graph.txt` | 让 AI 依赖被注入的图状态 |

### 1.3 相对合理的改动（保留）

- `SessionDesignApprovalDock` + CSS：专用审批面板。
- `design_finalize_change`：two-stage approval 终稿提交。
- `formatPendingDelta` 语义化：终稿展示人类可读。
- `message-part.tsx` 固定 design subagent subtitle：避免泄露 prompt。
- UI i18n description key。
- agent 权限配置。
- `refine` 模式 / `force` / `abandoned`。
- `"graph-agent"` version source。

## 2. 正确的工作集机制

### 2.1 活跃工作集（Active Working Set）

- **长期、跨 session 的 cache/记忆**。
- **GraphAgent 不能直接访问**。
- **不由 Tool 工具操作**，由数据库查询/写入事件自动触发更新。
- 有**容量上限**和**淘汰机制**。
- 子代理 session 启动时，临时工作集从活跃工作集复制初始化。

### 2.2 临时工作集（Temporary Working Set）

- **当前子代理 session 的语义视图**。
- **从活跃工作集复制初始化**。
- **无容量上限，不淘汰**。
- 存储的是**轻量语义条目**（名称 + 类型 + 简要语义），不是裸 ID，也不是完整实体 dump。
- GraphAgent 可以直接读取。
- GraphAgent 的任何查询/展开/搜索/写入行为都会自动扩展临时工作集，同时结果也会进入活跃工作集。

### 2.3 两者的关系

```
活跃工作集（长期记忆，不可见）
    ↓ 复制
临时工作集（当前 session 语义视图，可见）
    ↑ 扩展
GraphAgent
```

### 2.4 轻量语义条目

```ts
interface WorkingSetEntry {
  id: string
  name: string
  type: "context" | "node" | "prototype"
  briefSemantics: string
}
```

示例：
- `{ id: "ctx-xxx", name: "太空探索", type: "context", briefSemantics: "涵盖星际航行、天体探索的核心玩法上下文" }`
- `{ id: "node-yyy", name: "海", type: "node", briefSemantics: "海洋/海域概念" }`

## 3. GraphAgent 工具集重新设计

### 3.1 查询工具（只读）

| 工具 | 输入 | 输出 | 副作用 |
|---|---|---|---|
| `design_get_temporary_working_set` | 无 | 临时工作集中所有轻量语义条目 | 无 |
| `design_get_concept` | `name_or_id` | 概念完整信息 | 该概念加入临时/活跃工作集 |
| `design_get_context` | `name_or_id` | 上下文及其节点摘要 | 该上下文加入临时/活跃工作集 |
| `design_expand_node` | `name_or_id` | 节点的一跳邻居及关系 | 邻居加入临时/活跃工作集 |
| `design_search_graph` | `query` | 匹配的节点/上下文/原型摘要 | 匹配结果加入临时/活跃工作集 |
| `design_get_state_summary` | 无 | 图的整体统计 | 无 |
| `design_list_prototypes` | 无 | 所有关系原型 | 无 |

### 3.2 写入工具（只写 accumulator）

| 工具 | 输入 | 输出 | 副作用 |
|---|---|---|---|
| `design_define_context` | `name, semantics` | 新上下文摘要 | 入 accumulator，加入临时/活跃工作集 |
| `design_define_concept` | `name, context, ...` | 新概念摘要 | 入 accumulator，加入临时/活跃工作集 |
| `design_refine_concept` | `concept, ...` | 更新摘要 | 入 accumulator |
| `design_withdraw_concept` | `concept, cascade` | 删除摘要 | 入 accumulator |
| `design_relate_concepts` | `from, to, relation, ...` | 关系摘要 | 入 accumulator，相关节点加入临时/活跃工作集 |
| `design_withdraw_relation` | `from, to` | 删除摘要 | 入 accumulator |
| `design_define_relation_prototype` | `name, semantics, ...` | 新原型摘要 | 入 accumulator |
| `design_finalize_change` | 无 | 终稿审批 | 提交 accumulator，清空 accumulator |

### 3.3 移除的工具

从 GraphAgent 工具集中移除：
- `design_workset_get` / `design_workset_add` / `design_workset_remove` / `design_workset_expand`
- `design_get_design`（功能被覆盖）
- `design_resolve_reference`（会自动创建节点，不是纯查询）
- `design_get_relations`（功能被 `design_get_concept` 和 `design_expand_node` 覆盖）

## 4. GraphAgent 工作流程示例

用户说“船”：

1. 启动子代理，临时工作集从活跃工作集复制，包含“海”等之前讨论的概念。
2. GraphAgent 调用 `design_get_temporary_working_set`，看到“海、玩家、飞船、星球……”。
3. GraphAgent 注意到“海”可能与“船”相关，调用 `design_get_concept("海")` 获取详情。
4. 系统返回“海”的完整信息，同时把“海”加入/更新到临时/活跃工作集。
5. GraphAgent 发现“海”关联很多概念但没看到“船”，调用 `design_expand_node("海")`。
6. 系统把“海”的一跳邻居加入临时/活跃工作集，返回邻居详情。
7. GraphAgent 还是没看到“船”，调用 `design_search_graph("船")`。
8. 系统在 DB 中找到“船”，把它加入临时/活跃工作集，返回“船”的详情。

下次新 session 启动时，“海”和“船”已在活跃工作集里，临时工作集初始化就会包含它们，保持连续性。

## 5. Prompt 设计

### 5.1 用户消息（User Message）

```text
mode: cognition
request: 请帮我设计“船”这个概念在当前游戏中的作用。

当前活跃工作集摘要（已从长期记忆加载到本次会话）：
- 上下文：太空探索、战斗系统
- 节点：海、玩家、飞船、星球、资源、任务、敌人、武器
- 设计图版本：7

请先读取临时工作集了解当前上下文，然后按需查询和展开相关概念。
```

**不包含**：完整 graphState、临时工作集 JSON、大量 ID。

### 5.2 System Prompt（`graph.txt`）

需要包含：
1. GraphAgent 身份和职责。
2. 可用工具列表，明确区分查询工具和写入工具。
3. 工作集机制说明：
   - 活跃工作集是长期记忆，系统自动维护，GraphAgent 不可直接访问。
   - 临时工作集是当前会话的语义视图，从活跃工作集复制而来。
   - 每次查询、展开、搜索、写入都会自动扩展临时工作集和活跃工作集。
4. **明确声明**：图状态不会注入 prompt，必须通过 `design_get_temporary_working_set`、`design_search_graph`、`design_expand_node` 等工具获取。
5. two-stage approval 流程（judge → refine → finalize）。

## 6. 与 OpenCode 上游架构的对照

从 `https://github.com/anomalyco/opencode` 拉取干净 `dev` 分支后确认：

- 上游没有 design/GraphAgent 子系统，当前项目的 design 是自有实现。
- 上游 `task` 工具没有 `system` 参数，`task` 只是子代理启动器，把 `prompt` 作为用户消息传给子代理。
- 上游 `PromptInput.system` 是 session/LLM 编排层保留字段，没有工具从参数注入它。
- 上游 agent 通过 `prompt` 字段承载系统提示词，通过 instruction 系统注入额外上下文。
- 上游子代理对话框原样显示 `prompt` 内容，所以正确做法是让 prompt 本身人类可读。

**结论**：我通过 `task` 参数注入 `system` 是严重偏离；给 GraphAgent 的系统级说明应放在 `graph.txt`（agent prompt），而不是 task 参数。

## 7. 代码修改计划

### 阶段 1：止血（立即执行）

1. **删除 `packages/opencode/src/tool/task.ts` 中的 `system` 参数**
   - 移除 `BaseParameterFields` 中的 `system` 字段。
   - 移除 `runTask` 中 `ops.prompt({ ..., system: params.system })`。

2. **恢复 `packages/opencode/src/tool/design.ts` 中 `buildGraphAgentPrompt`**
   - 返回类型从 `{ prompt, system }` 恢复为 `string`。
   - 移除 `system` 相关拆分逻辑。
   - 调用处（`design_ask_graph`、`design_request_change`、`design_summarize_design`）恢复为直接传入 prompt 字符串。

3. **从 prompt 中移除完整 graphState JSON**
   - 删除 `contexts`、`nodes`、`edges`、`prototypes` 注入。
   - 删除 ID 语义化装饰逻辑。
   - 只保留：mode、request、userInput、activeWorkingSet 轻量摘要（名称）、knownVersion。

4. **更新 `packages/opencode/src/design/agent/prompt/graph.txt`**
   - 删除“图状态以 JSON 附加在 system prompt 末尾”的说明。
   - 恢复为：图状态不会注入 prompt，必须通过工具读取。

### 阶段 2：重构工作集数据模型

1. **修改 `packages/opencode/src/design/system/temporary-working-set.ts`**
   - 将 `TemporaryWorkingSet` 改为轻量语义条目集合：
     ```ts
     interface WorkingSetEntry { id, name, type, briefSemantics }
     interface TemporaryWorkingSet { entries: WorkingSetEntry[] }
     ```
   - 移除 `capacity`、移除或弱化 `systemAnalysis` / `expandedByGraphAgent`。
   - 保留 `get`、`reset`、`destroy`。
   - 新增内部 `addEntry(sessionID, entry)` 方法，不暴露为 AI 工具。

2. **修改 `packages/opencode/src/design/core/working-set.ts`**
   - 将活跃工作集从 ID 数组改为与临时工作集同构的 `WorkingSetEntry[]`。
   - 实现 LRU 淘汰。
   - 提供 `touch(entry)` 方法，由查询/写入事件调用。
   - 确认 `getNode`、`getContext`、`findNodesByName` 等查询是否触发 `touch`。

### 阶段 3：重新设计 GraphAgent 工具

1. **重写 `DesignWorksetGetTool` 为 `DesignGetTemporaryWorkingSetTool`**
   - 返回临时工作集的轻量语义条目列表。

2. **删除以下工具（从 `GraphAgentDesignTools` 中移除，必要时完全删除代码）**：
   - `DesignWorksetAddTool`
   - `DesignWorksetRemoveTool`
   - `DesignWorksetExpandTool`
   - `DesignGetDesignTool`
   - `DesignResolveReferenceTool`
   - `DesignGetRelationsTool`

3. **新增/修改查询工具**：
   - `DesignExpandNodeTool`：按名称/ID 展开节点，把邻居加入临时/活跃工作集。
   - `DesignSearchGraphTool`：全局搜索，把匹配结果加入临时/活跃工作集。
   - `DesignGetStateSummaryTool`：返回图统计摘要。

4. **给现有查询/写入工具添加 `touchEntry` 副作用**：
   - `design_get_concept` / `design_get_context` 被调用时，把目标加入工作集。
   - 所有写入工具成功后，把新实体加入工作集。

### 阶段 4：更新 `graph.txt`

1. 重新编写可用工具列表，区分查询和写入。
2. 说明工作集机制和自动扩展行为。
3. 明确禁止 AI 期望 prompt 中包含图状态。
4. 保留 two-stage approval 流程。

### 阶段 5：验证

1. `bun run typecheck` in `packages/opencode` / `packages/session-ui` / `packages/app`。
2. `bun run build` in `packages/app`。
3. GUI 验证：
   - 子代理对话框显示干净请求文本，无 JSON。
   - GraphAgent 调用 `design_get_temporary_working_set` 能获取初始工作集。
   - `design_search_graph` / `design_expand_node` 自动扩展工作集。
   - 写入和 `design_finalize_change` 正常工作。

## 9. 总结

- **问题根源**：把全量图状态注入 prompt，绕过了工作集机制。
- **正确机制**：活跃工作集和临时工作集是同构的轻量语义条目集合；临时工作集是当前 session 视图，活跃工作集是长期记忆。
- **修正方向**：移除 prompt 注入，让 GraphAgent 通过工具读取临时工作集；查询/展开/搜索/写入自动扩展工作集；恢复通用 `task` 工具。
- **保留功能**：审批面板、two-stage approval、语义化终稿展示、固定 agent description subtitle。
