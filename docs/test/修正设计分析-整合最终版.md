# GraphAgent 架构修正最终方案（整合版）

## 1. 问题根源：三次在错误方向上的修补

### 1.1 第一轮：把完整图状态塞进 prompt

最初在 `buildGraphAgentPrompt` 中把整个 `graphState`（contexts、nodes、edges、prototypes、working sets、version）序列化为 JSON，作为子代理的 `prompt`。

**错误本质**：把工作集机制架空了。GraphAgent 不需要再使用工具读取图状态，因为 prompt 已经给了全部答案。

### 1.2 第二轮：把 ID 装饰成 `名称 (id)`

当子代理对话框出现大量 ID 时，没有意识到这是架构偏离，而是加入 `nodeName(id)`、`contextName(id)`、`prototypeName(id)` 查询，把所有 ID 装饰成 `名称 (id)`。

**错误本质**：在错误方向上继续修补。prompt 里仍然是一大段内部数据库状态，只是换了一种格式。

### 1.3 第三轮：把 JSON 从 user message 移到 system prompt

为了不让学生在子代理对话框看到巨型 JSON，给通用 `task` 工具新增 `system` 参数，让 `buildGraphAgentPrompt` 返回 `{ prompt, system }`，把 JSON 图状态塞进 `system` 字段。

**错误本质**：
- 严重破坏 `task` 工具的通用性。
- 把问题从“用户看得见”变成“用户看不见”，但架构问题没有解决。
- 绕过了 OpenCode 的 agent prompt、instruction、session context 等既有机制。
- 用胶水代码掩盖设计缺陷。

## 2. 正确的工作集模型

### 2.1 活跃工作集（Active Working Set）

- **生命周期**：长期持久化，跨 session。
- **可见性**：GraphAgent **不能直接访问**。
- **内容形式**：轻量语义条目（`id + name + type + briefSemantics`）。
- **容量**：有上限，超过后自动 LRU 淘汰。
- **更新方式**：
  - GraphAgent 对临时工作集的任何扩展（展开、搜索、获取、写入），结果同时进入活跃工作集。
  - ChatAgent 或其他系统调用 design 查询/写入时，相关实体也进入活跃工作集。
  - 活跃工作集是“用户长期关注什么”的自动学习结果。

### 2.2 临时工作集（Temporary Working Set）

- **生命周期**：一个 GraphAgent 子代理 session。
- **可见性**：GraphAgent 可以直接访问。
- **初始化**：从活跃工作集复制。
- **内容形式**：与活跃工作集同构的轻量语义条目。
- **容量**：无上限，不淘汰。
- **更新方式**：
  - 展开节点 → 邻居加入临时工作集。
  - 搜索图 → 匹配结果加入临时工作集。
  - 获取概念/上下文详情 → 该实体加入临时工作集。
  - 写入新实体 → 新实体加入临时工作集。

### 2.3 两者的关系

```
活跃工作集（长期记忆，GraphAgent 不可见）
    ↓ 复制
临时工作集（当前 session 视图，GraphAgent 可见）
    ↑ 扩展
GraphAgent
```

GraphAgent 只看到临时工作集。但它的每一次扩展都会同时反馈到活跃工作集，影响未来的 session 初始焦点。

### 2.4 轻量语义条目

```ts
interface WorkingSetEntry {
  id: string
  name: string
  type: "context" | "node" | "prototype"
  briefSemantics: string
}
```

示例：
- `{ id: "ctx-xxx", name: "太空探索", type: "context", briefSemantics: "涵盖星际航行、天体探索的核心玩法上下文" }`
- `{ id: "node-yyy", name: "海", type: "node", briefSemantics: "海洋/海域概念" }`

**关键**：工作集存的不是裸 ID，也不是完整实体 dump，而是“够让 GraphAgent 快速扫一眼并决定深入查看哪个”的轻量信息。

## 3. GraphAgent 工具集重新设计

### 3.1 查询工具（只读）

| 工具 | 输入 | 输出 | 副作用 |
|---|---|---|---|
| `design_get_temporary_working_set` | 无 | 临时工作集中所有轻量语义条目 | 无 |
| `design_get_concept` | `name_or_id` | 概念完整信息（语义、关系、邻居名称） | 该概念加入临时/活跃工作集 |
| `design_get_context` | `name_or_id` | 上下文及其节点摘要 | 该上下文加入临时/活跃工作集 |
| `design_expand_node` | `name_or_id` | 节点的一跳邻居及关系 | 邻居加入临时/活跃工作集 |
| `design_search_graph` | `query` | 匹配的节点/上下文/原型摘要 | 匹配结果加入临时/活跃工作集 |
| `design_get_state_summary` | 无 | 图的整体统计 | 无 |
| `design_list_prototypes` | 无 | 所有关系原型 | 无 |

### 3.2 写入工具（只写 accumulator）

| 工具 | 输入 | 输出 | 副作用 |
|---|---|---|---|
| `design_define_context` | `name, semantics` | 新上下文摘要 | 加入临时/活跃工作集，入 accumulator |
| `design_define_concept` | `name, context, ...` | 新概念摘要 | 加入临时/活跃工作集，入 accumulator |
| `design_refine_concept` | `concept, ...` | 更新摘要 | 入 accumulator |
| `design_withdraw_concept` | `concept, cascade` | 删除摘要 | 入 accumulator |
| `design_relate_concepts` | `from, to, relation, ...` | 关系摘要 | 相关节点加入临时/活跃工作集，入 accumulator |
| `design_withdraw_relation` | `from, to` | 删除摘要 | 入 accumulator |
| `design_define_relation_prototype` | `name, semantics, ...` | 新原型摘要 | 入 accumulator |
| `design_finalize_change` | 无 | 终稿审批 | 提交 accumulator，清空 accumulator |

### 3.3 移除的工具

从 GraphAgent 工具集中移除：
- `design_workset_get` / `design_workset_add` / `design_workset_remove` / `design_workset_expand`
- `design_get_design`（功能被 `design_get_temporary_working_set` + `design_get_state_summary` 覆盖）
- `design_resolve_reference`（会写入新节点，不适合作为查询工具）
- `design_get_relations`（功能被 `design_get_concept` 和 `design_expand_node` 覆盖）

## 4. GraphAgent 工作流程示例

用户说“船”：

1. 启动子代理，临时工作集从活跃工作集复制，包含之前讨论的概念，比如“海”。
2. GraphAgent 调用 `design_get_temporary_working_set`，看到：海、玩家、飞船、星球……
3. GraphAgent 注意到“海”可能与“船”相关，调用 `design_get_concept("海")` 获取详情。
4. 系统返回“海”的完整信息，并把“海”加入/更新到临时/活跃工作集。
5. GraphAgent 发现“海”关联很多概念但没看到“船”，调用 `design_expand_node("海")`。
6. 系统把“海”的一跳邻居加入临时/活跃工作集，返回邻居详情。
7. GraphAgent 还是没看到“船”，调用 `design_search_graph("船")`。
8. 系统在 DB 中找到“船”，把它加入临时/活跃工作集，返回“船”的详情。

下次新 session 启动时，“海”和“船”已在活跃工作集里，临时工作集初始化就会包含它们，保持连续性。

## 5. Prompt 设计

### 5.1 用户消息（User Message）

```text
mode: cognition
request: 请帮我设计“船”这个概念在当前游戏中的作用。

当前活跃工作集摘要（已从长期记忆加载到本次会话）：
- 上下文：太空探索、战斗系统
- 节点：海、玩家、飞船、星球、资源、任务、敌人、武器
- 设计图版本：7

请先读取临时工作集了解当前上下文，然后按需查询和展开相关概念。
```

**不包含**：完整 graphState、临时工作集 JSON、大量 ID。

### 5.2 System Prompt（`graph.txt`）

需要包含：
1. GraphAgent 身份和职责。
2. 工作集机制说明：
   - 活跃工作集是长期记忆，系统自动维护，GraphAgent 不可直接访问。
   - 临时工作集是当前 session 的语义视图，从活跃工作集复制而来。
   - 每次查询、展开、搜索、写入都会自动扩展临时工作集和活跃工作集。
3. **明确声明**：图状态不会注入 prompt，必须通过工具读取。
4. 可用工具列表，明确区分查询工具和写入工具。
5. two-stage approval 流程（judge → refine → finalize）。

## 6. 数据层改动

### 6.1 `TemporaryWorkingSet` 服务

当前：
```ts
export interface TemporaryWorkingSet {
  contextIds: string[]
  nodeIds: string[]
  edgeKeys: string[]
  systemAnalysis: ...
  expandedByGraphAgent: ...
}
```

改为：
```ts
export interface WorkingSetEntry {
  id: string
  name: string
  type: "context" | "node" | "prototype"
  briefSemantics: string
}

export interface TemporaryWorkingSet {
  entries: WorkingSetEntry[]
}
```

- 移除 `capacity`（临时工作集无上限）。
- 移除或弱化 `systemAnalysis` / `expandedByGraphAgent`。
- `get` 返回轻量条目列表。
- 新增内部方法 `addEntry(sessionID, entry)`，由工具层调用，不对 AI 暴露。

### 6.2 `WorkingSet`（活跃工作集）服务

当前使用 ID 数组：
```ts
{
  activeContextIds: string[]
  activeNodeIds: string[]
  capacity: number
}
```

改为与临时工作集同构：
```ts
{
  entries: WorkingSetEntry[]
  capacity: number
}
```

- 使用 LRU 淘汰。
- 提供 `touch(entry)` 方法，由查询/写入事件调用。
- GraphAgent 不能直接访问。

### 6.3 工具层改动

- 重写 `DesignGetTemporaryWorkingSetTool`。
- 删除 `DesignWorksetAddTool` / `DesignWorksetRemoveTool` / `DesignWorksetExpandTool`。
- 修改 `DesignGetConceptTool`、`DesignGetContextTool` 等查询工具，使其调用 `touchEntry`。
- 新增/修改 `DesignExpandNodeTool`、`DesignSearchGraphTool`。
- 所有写入工具成功后调用 `touchEntry`。

### 6.4 `buildGraphAgentPrompt`

- 移除完整 `graphState` JSON。
- 移除 `temporaryWorkingSet` JSON。
- 只保留 `activeWorkingSet` 的名称摘要。
- 恢复返回字符串。

### 6.5 `task.ts`

- 删除 `system` 参数。
- 恢复通用 task 工具的纯洁性。

## 7. 与 OpenCode 上游架构的对照

从 `https://github.com/anomalyco/opencode` 拉取干净 `dev` 分支后确认：

- 上游没有 design/GraphAgent 子系统；当前 design 子系统是自有实现。
- 上游 `task` 工具没有 `system` 参数，`task` 只是子代理启动器，把 `prompt` 作为用户消息传给子代理。
- 上游 `PromptInput.system` 是 session/LLM 编排层保留字段，没有工具从参数注入它。
- 上游 agent 通过 `prompt` 字段承载系统提示词，通过 instruction 系统注入额外上下文。
- 上游子代理对话框原样显示 `prompt` 内容，所以正确做法是让 prompt 本身人类可读。

**结论**：通过 `task` 参数注入 `system` 是严重偏离；GraphAgent 的系统级说明应放在 `graph.txt`（agent prompt）或 instruction 中。

## 8. 保留的合理功能

以下改动方向正确，应保留：

- `SessionDesignApprovalDock` 和对应 CSS：专用审批面板。
- `design_finalize_change`：two-stage approval 的终稿提交。
- `formatPendingDelta` 语义化：终稿展示人类可读。
- `message-part.tsx` 固定 design subagent subtitle：避免泄露 prompt。
- UI i18n description key。
- agent 权限配置。
- `refine` 模式 / `force` / `abandoned`。
- `"graph-agent"` version source。

## 11. 总结

- **问题根源**：把全量图状态注入 prompt，绕过了工作集机制。
- **正确机制**：活跃工作集和临时工作集是同构的轻量语义条目集合；临时工作集是当前 session 视图，活跃工作集是长期记忆。
- **修正方向**：移除 prompt 注入，让 GraphAgent 通过工具读取临时工作集；查询/展开/搜索/写入自动扩展工作集；恢复通用 `task` 工具。
- **保留功能**：审批面板、two-stage approval、语义化终稿展示、固定 agent description subtitle。
