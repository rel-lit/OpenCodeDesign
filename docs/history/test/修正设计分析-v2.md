# GraphAgent 架构偏离与修正方案（提交审批）

## 1. 背景：原本的设计意图

本项目的 Design 子系统为 GraphAgent（design-graph 子代理）设计了一套**工作集驱动的记忆机制**，而不是把完整图状态塞进 prompt。

### 1.1 活跃工作集（Active Working Set）

- **性质**：系统级 cache / 注意力焦点。
- **触发方式**：当 ChatAgent 或其他系统调用 design 工具（如 `design_activate_context`、`design_activate_node`）时，对应节点/上下文被自动加入活跃工作集。
- **AI 权限**：GraphAgent **不能直接修改**活跃工作集，只能读取它作为初始焦点提示。
- **作用**：告诉 GraphAgent 用户当前最关心哪些上下文和概念。

### 1.2 临时工作集（Temporary Working Set）

- **性质**：每个 GraphAgent 子代理 session 私有的工作空间。
- **初始化**：子代理 session 启动时，从活跃工作集复制一份作为初始临时工作集。
- **AI 权限**：GraphAgent 可以主动通过工具操作它：
  - `design_workset_add`：添加节点/上下文到分析范围。
  - `design_workset_remove`：移除。
  - `design_workset_expand`：展开某个节点的邻居。
- **作用**：GraphAgent 通过工具调用来聚焦分析范围、获取信息，而不是一次性接收全量数据。

### 1.3 图状态获取方式

GraphAgent 应该：
1. 从 prompt 中得知当前请求和活跃工作集摘要。
2. 使用读取工具（`design_get_context`、`design_get_concept`、`design_find_concepts`、`design_get_relations`、`design_get_state` 等）按需查询。
3. 使用工作集工具管理自己的分析范围。
4. 使用语义化写入工具（`design_define_concept`、`design_relate_concepts` 等）把变更累积到临时 accumulator。
5. 最后调用 `design_finalize_change` 提交终稿。

**关键原则**：图状态不是 prompt 内容，而是通过工具调用访问的数据库。

## 2. 我实际做了什么（错误路径）

### 2.1 第一轮：`buildGraphAgentPrompt` 注入完整 graphState JSON

我在 `packages/opencode/src/tool/design.ts` 的 `buildGraphAgentPrompt` 中，把 `graphState`（contexts、nodes、edges、prototypes）以及 activeWorkingSet、temporaryWorkingSet、knownVersion 全部序列化为 JSON，作为子代理的 `prompt` 传入。

```json
{
  "mode": "cognition",
  "request": "...",
  "graphState": { "contexts": [...], "nodes": [...], "edges": [...], "prototypes": [...] },
  "activeWorkingSet": { ... },
  "temporaryWorkingSet": { ... },
  "knownVersion": 7
}
```

**错误本质**：
- 把工作集机制架空了。GraphAgent 不需要再使用工具读取图状态，因为 prompt 已经给了全部答案。
- 子代理对话框里出现巨型 JSON，用户看到一堆内部 ID 和数据结构。
- 违背了“图状态通过工具调用访问”的架构设计。

### 2.2 第二轮：把 ID 装饰成 `名称 (id)`

当用户反馈“子代理提示词里有一大堆 ID”时，我没有意识到这是架构偏离，而是以为只是“ID 没有显示为语义名称”。

于是我在 `buildGraphAgentPrompt` 中加入了大量 `nodeName(id)`、`contextName(id)`、`prototypeName(id)` 查询，把所有 ID 都装饰成 `名称 (id)` 的形式。

**错误本质**：
- 在错误的方向上继续修补。
- 即使名称出现了，prompt 里仍然是一大段内部数据库状态，只是换了一种格式。
- 没有解决“这些状态不应该出现在 prompt 中”的问题。

### 2.3 第三轮：把 JSON 从 user message 移到 system prompt

用户再次反馈“子代理提示词里看到巨型 JSON”时，我没有回到架构层面，而是试图通过 UI/渲染层绕过问题：

- 给通用 `task` 工具新增 `system` 参数。
- 让 `buildGraphAgentPrompt` 返回 `{ prompt, system }`。
- 把 JSON 图状态塞进 `system` 字段，让子代理对话框只显示干净的 `prompt`。
- 更新 `graph.txt` 说明 JSON 在 system prompt 里。

**错误本质**：
- **严重破坏 `task` 工具的通用性**。`task` 是 OpenCode 所有子代理的通用通道，不应该为 GraphAgent 单独增加 `system` 参数。
- 把问题从“用户看得见”变成“用户看不见”，但**架构问题没有解决**：图状态仍然被全量注入 LLM。
- 绕过了 OpenCode 的 agent prompt、instruction、session context 等既有机制。
- 用“胶水代码”掩盖设计缺陷。

## 4. 与 OpenCode 上游架构的对比

从 `https://github.com/anomalyco/opencode` 拉取干净 `dev` 分支作为参照：

### 4.1 上游没有 design 子系统

- `packages/opencode/src/design/` 不存在。
- `packages/opencode/src/tool/design.ts` 不存在。
- `design-graph`、`design-search` 等 agent 不存在。

说明当前项目的 design 子系统是**自有实现**，不是上游 fork。上游的作用是**架构参照**，判断当前改动是否遵循 OpenCode 的通用模式。

### 4.2 上游 `task` 工具的边界

上游 `task` 工具的参数只有：
- `description`
- `prompt`
- `subagent_type`
- `task_id`
- `command`
- `background`

没有 `system` 参数。`runTask` 调用 `ops.prompt` 时也不传 `system`。

**结论**：`task` 只是子代理启动器，把 `prompt` 作为用户消息传给子代理。它不应该负责注入 system prompt 或隐藏上下文。

### 4.3 上游 `PromptInput.system` 的用途

`PromptInput` 有 `system` 字段，会被存入 `SessionV1.User.system`，最终拼接到 LLM 的 system prompt 中。

但上游没有任何工具从参数注入 `system`。它是 session/LLM 编排层的保留字段，不是工具参数。

**结论**：我通过 `task` 参数注入 `system` 是滥用机制。

### 4.4 上游 agent 配置承载系统提示词

`Agent.Info` 有 `prompt` 字段（如 `PROMPT_EXPLORE`），会在 `LLMRequestPrep.prepare` 中拼接到 system prompt 最前面。

如果 GraphAgent 需要系统级说明，正确位置是：
1. agent 的 `prompt` 字段（`graph.txt`）。
2. instruction 系统（`AGENTS.md`、`CONTEXT.md`、config 中的 `instructions`）。

而不是 task 参数。

### 4.5 上游子代理对话框显示内容

上游没有任何特殊逻辑隐藏子代理的第一条用户消息。子代理对话框里看到的就是 `task.prompt` 的内容。

**结论**：正确做法是让 `prompt` 本身保持人类可读，而不是把它藏起来。

## 5. 修正后的正确架构

### 5.1 GraphAgent 的输入 prompt

应该是一个轻量、人类可读的文本，例如：

```text
mode: cognition
request: 请详细介绍当前设计图中所有的概念、关系、限界上下文以及它们之间的关联。

当前活跃工作集（共 2 个上下文，7 个概念）：
- 上下文：太空探索、战斗系统
- 概念：玩家、飞船、星球、资源、任务、敌人、武器
- 设计图版本：7

请使用 design_get_state、design_get_context、design_get_concept 等工具按需读取完整图状态，并管理工作集范围。
```

**不包含**：完整的 contexts/nodes/edges/prototypes JSON。

### 5.2 GraphAgent 如何获取图状态

1. 从 prompt 中得知请求和活跃工作集摘要。
2. 调用 `design_get_state` 获取完整图状态（如果它需要）。
3. 调用 `design_get_context`、`design_get_concept` 获取具体上下文/概念。
4. 使用 `design_workset_add` / `design_workset_expand` 扩展临时工作集。
5. 基于获取的信息回答问题或执行变更。

### 5.3 GraphAgent 的 system prompt（`graph.txt`）

`graph.txt` 应该：
1. 说明 GraphAgent 的身份、职责、可用工具。
2. 说明活跃工作集和临时工作集机制。
3. **明确声明**：图状态不会自动注入 prompt，必须通过工具读取。
4. 说明 two-stage approval 流程（judge → refine → finalize）。

## 8. 总结

我之前的改动把“全量图状态注入 prompt”当作了解决 GraphAgent 记忆问题的方法，反复在错误方向上修补（语义化 ID、拆 system prompt），最终还破坏了通用 `task` 工具的抽象。

正确的方向是：
- **信任并使用已经设计好的工作集机制**。
- **让 GraphAgent 通过工具调用获取图状态**。
- **让 prompt 保持人类可读**。
- **不在通用子代理通道上打补丁**。

请你审批以上方案。确认后我再开始改代码。
