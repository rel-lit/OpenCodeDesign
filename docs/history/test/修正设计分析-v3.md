# GraphAgent 工具与工作集机制重新设计方案（提交审批 v3）

## 1. 设计意图的重新确认

经过沟通，原本的设计意图进一步明确：

### 1.1 活跃工作集（Active Working Set）

- **长期、跨 session 的 cache/注意力机制**。
- **不由 Tool 工具操作**，而是由数据库查询/写入事件自动触发更新。
- 当调用 `getNode`、`getContext`、`createNode`、`createEdge`、`updateNode` 等方法时，相关节点/上下文自动加入活跃工作集。
- 有**容量上限**和**淘汰机制**（当前实现为 capacity=20，LRU 式淘汰）。
- 子代理 session 启动时，临时工作集会复制活跃工作集作为初始焦点。

### 1.2 临时工作集（Temporary Working Set）

- **只存在于一个子代理 session 内**。
- **只保存索引**（contextIds、nodeIds、edgeKeys），不保存完整实体数据。
- **没有容量上限，不会淘汰**。
- 当 GraphAgent 查询临时工作集时，系统会自动根据索引从数据库拉取完整内容返回。
- GraphAgent 不需要手动“添加/移除/扩展”临时工作集；这些操作应该通过查询语义自动完成，或者通过专门的查询工具触发。

### 1.3 查询与写入工具必须区分

- **查询工具**：读取图状态、搜索、展开、获取临时工作集内容等。
- **写入工具**：定义上下文、概念、关系等，写入临时 accumulator，最终由 `design_finalize_change` 提交。
- 查询工具不应该修改状态；写入工具不应该返回大量数据。

## 2. 当前实现的问题

### 2.1 临时工作集被当成手动工具目标

当前 GraphAgent 可用的工具包括：
- `design_workset_get`
- `design_workset_add`
- `design_workset_remove`
- `design_workset_expand`

这暗示 GraphAgent 需要手动维护临时工作集。但根据新的设计意图，临时工作集应该是查询时的自动上下文，不需要 AI 手动 add/remove。

### 2.2 完整图状态被注入 prompt

`buildGraphAgentPrompt` 仍然把 `graphState` 完整 JSON 注入 system prompt（或之前是 user message）。

这导致：
- AI 看到大量内部 ID 和数据结构。
- 工作集机制被架空，AI 不需要使用查询工具。
- token 爆炸，子代理被无关信息淹没。

### 2.3 查询工具能力不足

当前查询工具：
- `design_get_design`：返回语义摘要（好）。
- `design_get_context`：获取单个上下文及概念。
- `design_get_concept`：获取单个概念及关系。
- `design_find_concepts`：按关键词查找概念。
- `design_get_relations`：获取概念的关系。
- `design_list_prototypes`：列出原型。
- `design_resolve_reference`：解析引用（会写入节点，属于写入/解析混合工具）。

缺少：
- **一次性获取整个临时工作集内容**的工具（索引 → 自动查数据库返回完整实体）。
- **按关键词搜索整个图**的工具（当前 `design_find_concepts` 只能搜概念名称/别名/语义，不能搜上下文、关系、原型）。
- **展开节点**的工具（返回节点相关的展开内容，如邻居、关系、上下文）。

### 2.4 `design_resolve_reference` 是混合工具

`resolveReference` 在找不到匹配时会自动创建节点，这是写入行为。它不应该被 GraphAgent 当作纯粹的查询工具使用。

## 3. 建议重新设计的 GraphAgent 工具集

### 3.1 查询工具（只读）

| 工具 | 输入 | 输出 | 说明 |
|---|---|---|---|
| `design_get_temporary_working_set` | 无 | 临时工作集中所有索引对应的完整实体数据 | 核心工具。返回当前 session 关注的所有上下文、节点、边、原型的完整信息。 |
| `design_search_graph` | `query: string` | 按关键词匹配到的上下文、节点、边、原型列表 | 全局搜索。可以搜名称、别名、语义、关系类型等。 |
| `design_expand_node` | `node_id: string` | 该节点的邻居节点、相关边、所属上下文 | 展开工具。自动把展开的邻居加入临时工作集。 |
| `design_get_context` | `name_or_id: string` | 上下文详情及其包含的节点 | 保留，但输出应更语义化。 |
| `design_get_concept` | `name_or_id: string` | 概念详情、关系、邻居 | 保留。 |
| `design_get_relations` | `concept_id: string` | 概念的关系列表 | 保留。 |
| `design_list_prototypes` | 无 | 所有关系原型 | 保留。 |
| `design_get_state_summary` | 无 | 整个图的统计摘要（context/node/edge/prototype 数量） | 新增轻量工具。 |

### 3.2 写入工具（只写 accumulator）

| 工具 | 输入 | 输出 | 说明 |
|---|---|---|---|
| `design_define_context` | `name, semantics` | 创建上下文（入 accumulator） | 保留。 |
| `design_define_concept` | `name, context, kind, semantics, aliases` | 创建概念（入 accumulator） | 保留。 |
| `design_refine_concept` | `concept, semantics, aliases, kind` | 更新概念（入 accumulator） | 保留。 |
| `design_withdraw_concept` | `concept, cascade` | 删除概念（入 accumulator） | 保留。 |
| `design_relate_concepts` | `from, to, relation, semantics, constraints` | 创建/更新关系（入 accumulator） | 保留。 |
| `design_withdraw_relation` | `from, to` | 删除关系（入 accumulator） | 保留。 |
| `design_define_relation_prototype` | `name, semantics, constraints` | 创建原型（直接落库） | 保留。 |
| `design_finalize_change` | 无 | 提交终稿审批 | 保留。 |

### 3.3 移除的工具

- `design_workset_add`
- `design_workset_remove`
- `design_workset_expand`
- `design_workset_get`（被 `design_get_temporary_working_set` 替代）
- `design_resolve_reference`（从 GraphAgent 工具集中移除；可以保留给 ChatAgent 或其他入口使用，但 GraphAgent 不应使用它会自动创建节点的特性）
- `design_get_design`（功能被 `design_get_temporary_working_set` 和 `design_get_state_summary` 覆盖）

## 4. 临时工作集的自动更新机制

临时工作集不应该由 AI 手动维护，而应该由以下查询行为自动更新：

1. **子代理 session 启动时**：临时工作集 = 活跃工作集副本。
2. **调用 `design_search_graph`**：搜索结果自动加入临时工作集。
3. **调用 `design_expand_node`**：展开的邻居自动加入临时工作集。
4. **调用 `design_get_context` / `design_get_concept`**：被查询的上下文/概念自动加入临时工作集。
5. **调用写入工具创建新节点/关系时**：新实体自动加入临时工作集。

这样 AI 只需要关心“查什么”，系统会自动维护临时工作集。

## 5. 活跃工作集的自动更新机制

活跃工作集由以下事件自动触发：

1. **查询事件**：`getNode`、`getContext`、`getPrototype` 等查询命中时，对应节点/上下文加入活跃工作集。
2. **写入事件**：`createNode`、`createEdge`、`updateNode`、`createContext` 等成功后，相关节点/上下文加入活跃工作集。
3. **容量超限**：使用 LRU 或类似机制淘汰最早/最少使用的项。

当前 `design.ts` 中 `createNode`、`updateNode`、`createEdge`、`updateEdge`、`deleteEdge`、`resolveReference` 等已经调用了 `workingSet.activateNode`，方向正确。但需要确认：
- `getNode`、`getContext`、`getPrototype` 等查询是否也应该触发 activate？
- `findNodesByName` 是否应该激活命中的节点？
- 淘汰机制是否已经实现？

## 6. GraphAgent 的 prompt 应该包含什么

### 6.1 用户消息（User Message）

只包含：
- `mode`
- `request`（用户原始请求或 ChatAgent 转述的意图）
- `userInput`（如有）
- `knownVersion`（设计图版本号）
- `activeWorkingSet` 的轻量摘要（名称 + ID，不展开实体）
- `changePlan`（refine 模式下）
- `force`（refine 模式下）

**不包含**：`graphState`、`temporaryWorkingSet` 的完整 JSON。

### 6.2 System Prompt（来自 agent 配置 `graph.txt`）

包含：
- GraphAgent 身份和职责。
- 可用工具列表（查询工具、写入工具）。
- 工作集机制说明：活跃工作集是初始焦点，临时工作集随查询自动扩展。
- two-stage approval 流程说明。
- **明确声明**：图状态不会自动注入 prompt，必须通过 `design_get_temporary_working_set`、`design_search_graph`、`design_expand_node` 等工具获取。

## 7. 具体代码修改计划

### 7.1 第一步：修复 prompt 注入问题

1. **删除 `packages/opencode/src/tool/task.ts` 中的 `system` 参数**。
2. **恢复 `packages/opencode/src/tool/design.ts` 中 `buildGraphAgentPrompt` 返回字符串**。
3. **从 prompt 中移除完整 graphState JSON**，只保留轻量摘要。
4. **删除 `graph.txt` 中关于 system prompt JSON 的说明**。

### 7.2 第二步：重新设计 GraphAgent 查询工具

1. **新增 `design_get_temporary_working_set`**
   - 无输入。
   - 输出：临时工作集中所有索引对应的完整实体数据（上下文、节点、边、原型）。
   - 实现：调用 `design.getTemporaryWorkingSet(sessionID)`，然后根据索引从 graph 查询完整数据，格式化为人类可读文本。

2. **新增 `design_search_graph`**
   - 输入：`query: string`。
   - 输出：匹配的上下文、节点、边、原型列表。
   - 实现：搜索名称、别名、语义、关系类型等。
   - **副作用**：把匹配结果加入临时工作集。

3. **新增 `design_expand_node`**
   - 输入：`node_id: string`。
   - 输出：该节点的邻居节点、相关边、所属上下文。
   - 实现：调用 `graph.listEdgesForNode(nodeId)`，查询邻居和关系。
   - **副作用**：把邻居加入临时工作集。

4. **保留并改进现有查询工具**
   - `design_get_context`
   - `design_get_concept`
   - `design_get_relations`
   - `design_list_prototypes`
   - 给它们添加副作用：被查询的实体自动加入临时工作集。

5. **新增 `design_get_state_summary`**
   - 输入：无。
   - 输出：图的统计摘要（context/node/edge/prototype 数量）。

### 7.3 第三步：移除 GraphAgent 不需要的工具

1. 从 `GraphAgentDesignTools` 中移除：
   - `DesignWorksetGetTool`
   - `DesignWorksetAddTool`
   - `DesignWorksetRemoveTool`
   - `DesignWorksetExpandTool`
   - `DesignGetDesignTool`
   - `DesignResolveReferenceTool`（从 GraphAgent 中移除，可保留给 ChatAgent）

2. 如果 `design_workset_*` 工具没有其他地方使用，可以考虑完全删除相关代码。

### 7.4 第四步：调整 `TemporaryWorkingSet` 服务

1. 移除 `update` 和 `expand` 接口（不再需要 AI 手动更新）。
2. 保留 `get`、`reset`、`destroy`。
3. 新增内部方法或让查询工具直接调用 `update`，但不对 AI 暴露为工具。
4. 移除 `capacity` 限制（临时工作集无上限）。

### 7.5 第五步：调整 `WorkingSet`（活跃工作集）

1. 确认查询操作是否触发 `activateNode`/`activateContext`。
2. 确认淘汰机制是否按 LRU 工作。
3. 如有需要，把活跃工作集的更新封装成统一事件。

### 7.6 第六步：更新 `graph.txt`

1. 重新编写可用工具列表，区分查询工具和写入工具。
2. 说明临时工作集如何自动扩展。
3. 说明活跃工作集是初始焦点，由系统自动管理。
4. 明确禁止 AI 期望 prompt 中包含完整图状态。

## 8. 需要确认的问题

1. **临时工作集的副作用是否应该由查询工具触发？**
   - 例如 `design_search_graph` 自动把结果加入临时工作集。
   - 还是让 AI 显式调用某个工具来“加载到工作集”？

2. **`design_get_temporary_working_set` 返回的格式？**
   - 纯文本摘要？
   - 还是结构化 JSON？（建议纯文本，因为 AI 读取工具输出也是文本）

3. **`design_search_graph` 的搜索范围？**
   - 是否搜索已 accumulator 中的 pending changes？
   - 是否搜索 retired 节点？

4. **`design_resolve_reference` 是否要保留给 GraphAgent？**
   - 它会自动创建节点，属于写入行为。
   - 建议 GraphAgent 使用 `design_search_graph` + `design_define_concept`，而不是 `resolve_reference`。

5. **`design_get_design` 是否要删除？**
   - 当前它返回语义摘要，可能有其他调用方。
   - 需要确认后再删除。

6. **活跃工作集的淘汰机制？**
   - 当前实现是否是 LRU？
   - 是否需要调整策略？

## 9. 验证计划

1. 类型检查：opencode / session-ui / app。
2. App 构建。
3. 运行 GraphAgent 测试：
   - 子代理对话框只显示干净请求文本。
   - GraphAgent 调用 `design_get_temporary_working_set` 能获取初始工作集内容。
   - GraphAgent 调用 `design_search_graph` 能找到相关内容并自动扩展工作集。
   - GraphAgent 调用 `design_expand_node` 能展开邻居。
   - 写入工具正常工作，最终 `design_finalize_change` 能提交。

## 10. 总结

当前最大的问题不是某个字段命名或渲染问题，而是：
- **GraphAgent 的记忆机制被 prompt 注入取代**。
- **临时工作集被错误地暴露为手动工具**。
- **查询/写入工具边界不清**。

本方案建议：
- 让 GraphAgent 通过专门的查询工具按需获取图状态。
- 临时工作集由系统自动维护，不对 AI 暴露 add/remove/expand 工具。
- prompt 只保留轻量上下文摘要。
- 修复之前对 `task` 工具和 `buildGraphAgentPrompt` 的架构偏离。

请审批此方案。
